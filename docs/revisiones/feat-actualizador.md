# Review: feat/actualizador — T10 updater

Static review against `docs/review-checklist.md`, the T10 card, `docs/spec.md` section 10.1, and the governing constitution, architecture and plan. Reviewed all five new production classes, their three test classes, and the existing contracts and relevant consumers. No production code or tests were changed. The architect reported a green build with **517 tests**; that is the architect's execution, not mine, and is not evidence against the findings below.

## Findings

- **F1 — blocking — `src/main/java/com/discordtowny/update/DefaultUpdateService.java:390`, `:433`, `:467`; `src/main/java/com/discordtowny/update/JdkHttpTransport.java:22`. The executable source is not fixed.** Only the initial API endpoint is constant. Asset URLs from JSON are used without validating HTTPS, host, repository or release path; the public download method also accepts an arbitrary URL. An API response naming an external or plain-HTTP jar and its matching digest reaches the success path. Checksum assets are equally unrestricted. Automatic redirects can change hosts even when the initial URL is official: JDK `NORMAL` prevents HTTPS-to-HTTP downgrade, but permits cross-host redirects. The transport discards the final URI and redirect history. **The fix must achieve:** every metadata, checksum and executable request must remain within an explicit official-source policy, including repository identity, HTTPS and permitted GitHub asset delivery redirects; reject untrusted destinations before contacting them. The constant alone cannot establish this property. [JDK redirect policy](https://docs.oracle.com/en/java/javase/25/docs/api/java.net.http/java/net/http/HttpClient.Redirect.html).

- **F2 — blocking — `src/main/java/com/discordtowny/update/DefaultUpdateService.java:55`, `:396`, `:425`, `:436`. Checksum extraction can accept malformed input and is not bound to the selected jar.** The release-body regex has no boundary after its 64 hex digits. Publishing `SHA-256: ` followed by the correct digest plus one extra hex digit yields the correct 64-digit prefix, so a wrong-length published checksum can lead to `SUCCESS`. Separately, the last eligible jar and last checksum asset win, while the first 64-hex token anywhere in that asset wins. For `checksums.txt` with a sources-jar digest first and the runnable-jar digest second, the updater selects the sources digest and rejects a legitimate runnable jar. It neither matches filenames nor rejects ambiguous artifact choices; a body digest takes precedence over any correctly paired checksum file. **The fix must achieve:** select the intended executable unambiguously, bind its exact published checksum to that artifact, and reject missing, empty, malformed, wrong-length or ambiguous checksum data without staging a jar. The raw `Release.sha256()` equality check at line 515 does reject malformed strings passed directly; the extraction step is where malformed input can become apparently valid.

- **F3 — blocking — `src/main/java/com/discordtowny/update/DefaultUpdateService.java:531`, `:554`, `:568`. Failure cleanup covers the source temp path, not a partially published destination.** When atomic movement is unsupported, the fallback move can fail with an incomplete destination. Every catch/finally cleans only `tempFile`; `DiscordTowny.jar` can remain in the directory Paper will inspect, and line 195 treats any nonempty regular file there as pending. Java explicitly leaves source and destination state undefined after a failed non-atomic move. Deletion errors are also swallowed, so even checksum refusal can claim “discarded” while its temp file remains. **The fix must achieve:** publication must not expose an incomplete executable, every failed transfer/publication must account for all files it created while preserving any previously verified pending update, and cleanup failure must be visible rather than claimed as successful disposal. [JDK file-move contract](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/nio/file/Files.html#move(java.nio.file.Path,java.nio.file.Path,java.nio.file.CopyOption...)).

- **F4 — blocking — `src/main/java/com/discordtowny/update/DefaultUpdateService.java:134`, `:522`, `:523`. Active-jar protection compares path spelling, not the actual destination.** With an existing `plugins/update` directory, an update folder of `plugins/update/..`, target `DiscordTowny.jar`, and active path `plugins/DiscordTowny.jar`, absolute paths compare unequal although the move replaces the active jar. A parent-directory symlink/junction can produce the same alias. The extended constructor also accepts absolute or traversing target names. These are local path/wiring conditions, not a claimed remote filename injection. **The fix must achieve:** constrain the target to the intended update directory and establish that its resolved destination cannot be the active jar before any publication, including normalized paths and parent-directory aliases. The current tests exercise only distinct ordinary paths.

- **F5 — blocking — `src/main/java/com/discordtowny/update/JdkHttpTransport.java:44`; `src/main/java/com/discordtowny/update/DefaultUpdateService.java:499`, `:584`, `:171`. The maximum timeout does not cover streamed response bodies.** `ofInputStream()` returns before the body is fully received. In the JDK 25 implementation, the response timer is cancelled before body consumption; the service supplies no body deadline. A peer can deliver headers and some bytes, then keep the connection open indefinitely. A jar download retains its partial temp file and a common-pool worker; metadata/checksum reads can hang similarly. Periodic scheduling submits further work without waiting, and `stop()` cancels the scheduler task, not those submitted operations. **The fix must achieve:** bounded completion across redirects and the complete metadata/checksum/jar body, cancellation that actually terminates I/O and cleans partial files, and shutdown that prevents outstanding work from publishing afterwards. A future timeout alone must not leave its download running. [JDK streaming-body contract](https://docs.oracle.com/en/java/javase/25/docs/api/java.net.http/java/net/http/HttpResponse.BodyHandlers.html#ofInputStream()), [OpenJDK 25 timer and body flow](https://github.com/openjdk/jdk25u/blob/master/src/java.net.http/share/classes/jdk/internal/net/http/MultiExchange.java).

- **F6 — important — `src/main/java/com/discordtowny/update/DefaultUpdateService.java:305`, `:317`, `:322`. Breaking-change notices and their confirmation gate are absent.** A newer release whose notes announce breaking configuration changes or required migration is downloaded automatically under the default settings. `notes` is stored but never used in notices or download authorization; no notice includes the required changes summary. This is service behavior already present, independent of the accepted absence of command wiring. **The fix must achieve:** the section 10.1 notice content and a confirmation boundary that prevents such releases from being automatically staged before the required acknowledgement. If the release format has no agreed way to identify this condition, resolve that contract with the architect rather than inventing an undocumented heuristic.

- **F7 — blocking — `src/main/java/com/discordtowny/update/DefaultUpdateService.java:221`, `:226`, `:317`, `:547`. Player-facing update text bypasses the language catalog.** Join notifications send literal English and audit details contain literal English that the existing log renderer prints directly (`src/main/java/com/discordtowny/discord/JdaDiscordGateway.java:353`). Selecting Spanish or editing the message files cannot affect these strings, so acceptance criterion 12 cannot pass for this feature. Existing `updates.available` and `updates.downloaded` keys are present in both catalogs with matching placeholders. **The fix must achieve:** player and Discord notification text must use the configured, reloadable message catalog and appropriate chat/label formatting; console output must remain English. Any additional catalog requirements outside this task's zone must be coordinated, not bypassed with literals.

- **F8 — important — `src/main/java/com/discordtowny/update/DefaultUpdateService.java:261`, `:278`, `:322`. Conditional caching can permanently suppress recovery.** The ETag is committed before the body has been read or parsed. A truncated response with a new ETag leaves a null or older cached release, and subsequent `304` responses retain that wrong state. Even after a successful metadata read, if the jar download fails once, later `304` responses return before auto-download is considered, so connectivity recovery does not retry the available update. A failed checksum-asset request can similarly cache a release with no checksum indefinitely. **The fix must achieve:** validators and usable cached content must remain consistent, and unchanged metadata must still allow unfinished checksum acquisition/download work to recover without a new release or server restart.

- **F9 — important — `src/main/java/com/discordtowny/update/DefaultUpdateService.java:253`, `:323`, `:441`, `:539`, `:553`. Failure reporting does not reliably represent the operation outcome.** Receiving headers resets the suppression flag before the metadata body is read. Repeated body-read failures therefore each emit a warning despite no complete successful check between them. Conversely, automatic downloads normally return failure enum values, but their completion handler inspects only `err`; HTTP failures, disk-full errors and transport I/O failures can disappear without the required report. A checksum fetch catches all exceptions and converts an unavailable checksum into a missing one, losing the cause. After a successful move, an audit callback or response-close exception is caught as a download failure even though the verified jar is already staged. **The fix must achieve:** retain outage suppression until a genuinely successful operation demonstrates recovery, distinguish unavailable reads from confirmed missing data, and consume/report non-success download results once with enough context to diagnose them. Permanent refusal, network failure and successful publication must remain distinguishable; notification failure must not misreport an already committed download.

- **F10 — important — `src/main/java/com/discordtowny/update/SimpleJson.java:228`, `:250`; `src/main/java/com/discordtowny/update/DefaultUpdateService.java:415`. Unbounded JSON nesting escapes the advertised malformed-response handling.** Objects and arrays recursively call `parseValue()` without a depth limit. An object containing tens of thousands of nested arrays fits comfortably under the 1 MiB metadata cap and exhausts the Java stack. `StackOverflowError` is not caught by either `catch (Exception)`; the check future completes exceptionally rather than producing the advertised handled failure. This is a bounded updater failure, not evidence that the whole Minecraft server crashes. **The fix must achieve:** reject excessive nesting as a controlled parse failure before stack exhaustion and exercise that boundary through the service, not just shallow malformed examples.

- **F11 — important — `src/main/java/com/discordtowny/update/SemanticVersion.java:115`. Prerelease ordering is not semantic version ordering.** Whole-string, case-insensitive comparison makes `1.0.0-beta.10` older than `1.0.0-beta.2`, and treats differently cased identifiers as equal. If such tags are compared, the service can miss an update or classify an older prerelease as newer. **The fix must achieve:** compare prerelease identifiers using numeric ordering for numeric identifiers and case-sensitive ASCII ordering for nonnumeric identifiers, including the specified identifier-count rules. [Semantic Versioning precedence rules](https://semver.org/#spec-item-11).

- **F12 — important — `src/main/java/com/discordtowny/update/DefaultUpdateService.java:266`, `:345`. Secondary rate limits are ignored.** Backoff is recorded only when `X-RateLimit-Remaining` is exactly `0` and a reset header exists. A `429`/`403` with positive remaining quota and `Retry-After` returns cached data without setting any delay; the next requested check contacts GitHub immediately. **The fix must achieve:** enforce GitHub's retry delay for secondary limits as well as primary exhaustion, across subsequent checks. The existing test covers only a primary-limit `403`. [GitHub rate-limit handling](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api#exceeding-the-rate-limit).

- **F13 — important — `src/test/java/com/discordtowny/update/DefaultUpdateServiceTest.java:186`, `:425`, `:474`, `:693`, `:762`. Security tests overstate their guarantees, and notification completion is racy.** The streaming-cap test's entire 2 KiB body fits in the production 8 KiB read buffer and it never observes bytes consumed or writes before rejection; moving the cap check after the complete download would still pass. The Content-Length test likewise cannot distinguish rejection before reading from rejection after reading. The successful-download test checks final contents, not atomic publication: replacing the move with a non-atomic copy would pass. The repository test checks a literal constant, so redirecting actual requests elsewhere without changing that constant would pass. The notification test waits for file presence, then checks an audit event emitted afterwards; it can fail while the download worker has not yet emitted that event. **The fix must achieve:** observe bounded consumption and cancellation before EOF with absent and lying length headers, refusal before body reads for an oversized declared length, filesystem state under failed publication, and the destinations actually contacted/refused, and synchronize notification assertions with the observed notification or operation completion. Retain the useful final-state assertions; they are not substitutes for these properties.

The checksum proves that the received bytes have the same SHA-256 digest as the selected published value, subject to correct extraction and artifact association. It detects corruption or substitution when that expected value remains trustworthy. **It does not independently authenticate the author, establish that the jar is safe, or protect against compromise of the repository/release account that publishes both jar and checksum.** Someone controlling both can publish any executable with its matching digest. No signature or separate trust anchor is present, and adding one is not an undocumented requirement of this review. The fixed-source claim in `DefaultUpdateService.java:31` is nevertheless stronger than what this implementation enforces (F1); the checksum cannot repair that missing restriction.

Following every write: directories and randomized `.tmp` files are created at lines 463–464, body bytes go only to that temp file at 497/507, and the executable destination is changed only by moves at 530/532. No separate write targets `activeJarPath`. This supports ordinary-path isolation, but does not defeat the destination aliases in F4. A normal checksum mismatch or read/write exception reaches temp cleanup after streams close; refusal cannot pass the direct digest equality check. Cleanup guarantees fail under F3 and unbounded/uncancelled work under F5.

The byte cap itself is correctly checked before each chunk is written at lines 499–507, independent of `Content-Length`. Missing, understated, negative or unparseable length values do not disable that guard; a representable oversized value is rejected upfront. Metadata and checksum bodies also have byte caps. A huge declared length is not used for allocation. This is a source-level conclusion, not an executed streaming test.

An ordinary HTML body is rejected at the JSON value parser and handled by the service; a non-object root is also rejected. Nesting is the hostile-input gap in F10. An ordinary endless redirect chain is not itself an unlimited loop: the default JDK implementation bounds attempts (default five). That bound does not validate redirect destinations or bound a stalled body between redirects. [JDK HTTP retry limit](https://docs.oracle.com/en/java/javase/25/docs/api/java.net.http/module-summary.html).
