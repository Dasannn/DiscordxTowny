- **F6 — blocking — `src/main/java/com/discordtowny/DiscordTownyWiring.java:640-642`, `src/main/java/com/discordtowny/DiscordTownyPlugin.java:101-130`:** The three flags now stay false after their respective registration throws, and a *direct* second call to `registerListeners` retries only the failed registrations. - **F7 — follow-up — `src/main/java/com/discordtowny/update/DefaultUpdateService.java:395-427`, `src/test/java/com/discordtowny/DiscordTownyPluginTest.java:639-643`:** `getSeedProbeThread()` and its `AtomicReference<Thread>` exist solely for this test and have no production caller. Mockito static mocks are thread scoped, so the scheduler's real probe still runs on its worker. Await the returned seed future afterward and assert it found the staged jar. This directly checks the forbidden operations on the server thread, including construction and reload, without a production thread accessor.
- **F8 — follow-up — `src/main/java/com/discordtowny/update/DefaultUpdateService.java:406-418,514-534`:** The synchronized seed method memoises one future, so its calls from wiring and `start()` submit only once. `stop()` uses a different lock and shuts down the owned scheduler. If shutdown removes a queued seed task, its `CompletableFuture` can remain incomplete indefinitely; a later call returns that same future. If first called after `close()`, the method falls back to `executor` and runs a probe on a closed service. The production constructor initializes `executor` to the common pool, making the final common-pool fallback redundant. A caller-supplied direct executor can run the fallback probe on the caller thread, contradicting the method's zero-I/O-on-caller claim. Guard the stopped state and settle or cancel the pending seed future as part of shutdown; keep any executor fallback off the caller thread.
- **F9 — follow-up — `src/main/java/com/discordtowny/update/DefaultUpdateService.java:554-556`, `docs/informes/T25-join-notice.md:105`:** `isCachedUpdatePending()` has no production caller, is absent from `UpdateService` at this tip, and serves only test assertions. ## Verified by inspection

- **F4 reload path:** The constructor no longer calls `Files`. Both initial wiring and reload submit the seed before publishing the updater; `start()` calls the memoised method again. The normal service owns a dedicated scheduler, so its probe is submitted off the server thread. A seed that sees `false` leaves a newer download's `true` flag intact. The current reload test checks the worker thread, although the direct main-thread assertion in F7 is stronger.
- **F5 registration:** Each listener has its own flag set after `registerEvents` returns; synchronized `registerListeners` prevents concurrent callbacks from registering the same listener twice. On a subsequent callback, a failed listener alone retries. Flags reset on `onDisable`; a normal reload without disable leaves successful listeners registered, and their suppliers reference the current wiring. The tests exercise the real plugin registration method, but manually supply the retry callback that healthy reload does not dispatch. If Bukkit could register a listener and then throw, a flag alone could not prove exact-once registration; no such partial Bukkit behavior is established here.
- **Shutdown and executors:** The normal wiring path uses a dedicated `dt-update-scheduler` thread; neither `start()` nor a second seed call submits another probe. `isShutdown()` followed by submission is not atomic: concurrent close can still cause `RejectedExecutionException`. This is outside the ordinary serialized reload path but reinforces F8's need for a defined stopped outcome.
