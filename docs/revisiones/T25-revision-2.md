## Findings

- **F4 — blocking — `src/main/java/com/discordtowny/DiscordTownyWiring.java:614-623`, `src/main/java/com/discordtowny/update/DefaultUpdateService.java:394-401`:** Normal startup constructs the updater inside `initializeServicesAsync`, launched on a virtual thread by `start()` (`DiscordTownyWiring.java:161-163`). `/dt admin reload` calls `wiring.reload()` on the server thread, however, and `reload()` constructs a new updater synchronously. The new constructor seed calls `Files.isRegularFile` and potentially `Files.size` there on every healthy reload and degraded recovery. The claim that construction is always off the server thread is false. Keep the seed on a worker during reload, or arrange for the disk probe outside construction so the reload path does not stat the update jar on the server thread.
- **F5 — important — `src/main/java/com/discordtowny/DiscordTownyPlugin.java:93-101`:** `compareAndSet(false, true)` marks registration complete before Bukkit registers anything. If either sync registration throws, the shared sync flag remains true and neither sync listener is retried; if update registration throws, its flag remains true and later recovery callbacks cannot register it. The catch only logs the failure. Track each successfully registered listener separately, marking it only after Bukkit returns, so a later eligible callback can retry only the missing registration. The lifecycle tests do not invoke this production method or simulate a registration failure.

## Verified by inspection

- **Join path:** `UpdateJoinListener.onPlayerJoin` calls `shouldNotifyAdminsOnJoin` and `notifyAdminOnJoin`. The latter reads `stagedUpdatePending`, `getLastCheckResult`, `messagesSupplier.get`, message rendering, `isBreaking`, `extractSummary`, and `formatCheckFailureReason`. Those paths use in-memory fields and text operations; none calls `Files`, `isUpdatePending`, a network check, or storage. The supplied messages reference in normal wiring is already loaded. A join with no service, degraded wiring, or no admin permission returns without a warning.
- **Cached state:** The constructor seed detects a staged jar at startup. Successful publication sets true; failed publication re-probes after rollback; `isUpdatePending()` re-probes and refreshes the flag for existing callers. Manual deletion after a true seed yields a **wrong downloaded notice** until a command/reload refreshes it. A second service staging a jar after this instance seeded false yields a **late notice** until a command/reload refreshes it. These are limits of the requested no-I/O join cache, rather than a separate blocking defect. There is also an unsynchronized probe/publication race: an `isUpdatePending()` probe can write an older false result after publication writes true, delaying the notice until the next probe.
- **Lifecycle:** Initial successful startup dispatches registration on the main thread. Initial degraded startup calls the callback but the guard skips registration; recovery reload dispatches again after storage is ready. Ordinary reload does not dispatch again and the existing listener's suppliers point to the same wiring object, so it sees the replacement service. `onDisable` stops and clears the wiring and resets both flags; Bukkit owns listener unregistration on plugin disable. The package-private `isXRegistered()` methods are read-only but unused even by the new tests; they add production surface solely for tests and can be removed.
- **Tests:** Deleting a staged jar before `notifyAdminOnJoin` would make the real-service tests fail if that method again called `isUpdatePending()` or used `Files.isRegularFile`/`Files.size` to decide the notice. They do not detect arbitrary new `Files` calls that leave the notice unchanged, and the stand-in listener test never executes `DefaultUpdateService`. The F1 lifecycle test copies the intended callback with its own flag; it does not exercise `DiscordTownyPlugin.registerListeners` or failure recovery. The wiring test verifies the post-start callback count. F3 now catches ordinary exceptions from `notifyAdminOnJoin`, logs the player's name and UUID at `WARNING`, and lets fatal `Error`s propagate.

**Verdict: blocked.** F4 puts the new disk probe on the server thread during reload; F5 can permanently suppress listener registration after a recoverable failure.
