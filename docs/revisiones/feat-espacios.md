# T6 review — feat/espacios

Static review of `DefaultSpaceService`, both files under `src/test/java/com/discordtowny/space/`, and the queue/executor/storage paths they actually use, against the T6 card, constitution, spec sections 3, 4.1 and 7, architecture and plan. No git or Gradle commands were run. The architect reported a green build with 275 tests; that is not reviewer execution evidence.

Executor findings below are dependency defects encountered through T6, not assertions that this branch introduced changes in `discord/`. They require coordination with that package's owner; the space author must not silently cross the exclusive file zone.

## Findings

- **blocking — F1: crash recovery can duplicate a channel.** `src/main/java/com/discordtowny/discord/JdaGuildOperationExecutor.java:102`, `:117`, `:447`, `:549`; reached from `src/main/java/com/discordtowny/space/DefaultSpaceService.java:121`. With both channel types enabled and 48 channels already in a category, creation adds text channel 49. Kill the process after Discord returns its ID but before `spaces.save` records it. On retry, capacity selection adds two requested channels to 49, rejects the original category and chooses another. Recovery searches for the unrecorded text channel only in that new category, so it creates a duplicate and leaves the original orphaned. IDs are normally saved between steps, but this return-to-write window is not covered. The fix must recover ownership of already-created resources before selecting capacity for genuinely missing channels, including after restart; verify this exact interruption without deleting history as compensation.
- **blocking — F2: name-based adoption can grant a town's access to unrelated members.** `src/main/java/com/discordtowny/discord/JdaGuildOperationExecutor.java:518` and `:550`. When no role ID is saved, `ensureRole` adopts the first matching guild role without proving plugin/town ownership. For a town whose generated role name matches an existing unrelated role, all existing holders of that role gain access to the newly created private channels. Channel recovery likewise adopts a matching channel without proving ownership or reapplying permissions. The fix must establish unambiguous managed ownership during recovery, reject collisions safely, and enforce the required permissions before success. Names alone cannot be the ownership check. This is a dependency issue that prevents T6 acceptance criterion 3.
- **important — F3: quota and cooldown admission are not atomic.** `src/main/java/com/discordtowny/space/DefaultSpaceService.java:93`, `:109`, `:119`. With one slot left, two distinct requests can both observe the old active count before either queued creation completes; both are then created. Concurrent requests by the same mayor can also both pass the separate cooldown check and write. Queue serialization does not serialize these earlier checks or reserve capacity. The fix must make admission account for pending creations and atomically enforce cooldown/quota, with failed admissions releasing any reservation; cover overlapping requests with controlled futures.
- **important — F4: invalid-input rejection is reported as an operational failure.** `src/main/java/com/discordtowny/space/DefaultSpaceService.java:71`; reinforced by `src/test/java/com/discordtowny/space/DefaultSpaceServiceTest.java:312`. A null request, missing town UUID or blank town name returns `FAILED` before any operation is attempted. This is a rejected precondition, contrary to the requested `CreateResult` semantics. The fix must distinguish invalid input from execution failure, using an exceptional invalid-argument result or an architect-approved contract change, and update the test. All eight current enum values otherwise have reachable return paths; there is no missing mayor-rejection enum because mayor verification is explicitly the caller's main-thread responsibility.
- **important — F5: restore/rename can report success while required channels are missing.** `src/main/java/com/discordtowny/discord/JdaGuildOperationExecutor.java:289`, `:298`, `:318`, `:169`; surfaced by `src/main/java/com/discordtowny/space/DefaultSpaceService.java:256` and `:175`. If a saved channel has been manually deleted, the executor skips it when lookup returns null and still returns success. Restore marks the space `ACTIVE` with the dead IDs; rename records the new name without renaming the missing resource. The service correctly checks the outcome, but that outcome does not establish the postcondition. The fix must report the missing required resource and retain a repairable inconsistent state, or complete an explicitly defined repair before success. Do not silently claim that lost history was restored. Test absent resources through the real executor.
- **important — F6: retrying an interrupted archive through create can reactivate inaccessible channels.** `src/main/java/com/discordtowny/space/DefaultSpaceService.java:94` and `:121`; `src/main/java/com/discordtowny/discord/JdaGuildOperationExecutor.java:208`, `:543`, `:584`, `:140`. If archiving deletes the role and then fails while moving channels, failure handling marks the space `INCONSISTENT`. `create` treats every such state as interrupted creation. Its executor creates a replacement role but returns the existing channels by ID without applying permissions for that role or moving archived channels back, then marks the space `ACTIVE`. Residents receive a role that cannot access the retained channels. The fix must preserve/recover lifecycle intent or otherwise ensure that this resume path completes the correct transition and its permission postconditions before reporting success.
- **important — F7: same-name recreation cannot restore the archived history.** `src/main/java/com/discordtowny/space/DefaultSpaceService.java:242`; `src/main/java/com/discordtowny/discord/JdaGuildOperationExecutor.java:264`. Both restore layers look up only the request's UUID. A deleted town recreated with the same name gets a different UUID, so restoration fails with “No space found”; ordinary creation also searches only the new UUID and can create a separate space. Spec 7 explicitly requires restoration in this case. The fix must provide a deliberate, unambiguous archived-space reassociation flow that retains the exact channel IDs/history and persists the new town identity, coordinated with the contract/storage owners.
- **important — F8: the interrupted-creation test supplies the behavior it claims to verify.** `src/test/java/com/discordtowny/space/DefaultSpaceServiceTest.java:349` and `:358`. The test never starts or interrupts actual creation: it inserts a partial row, and the mocked gateway writes the desired completed row using the original IDs. Assertions at lines 381–387 therefore establish admission of an inconsistent row and the stub's own output, not resumable creation or absence of duplicate Discord resources. Retain it as a delegation test if named accordingly; add a check that interrupts the real lifecycle after role creation and at the Discord-return/persistence boundary, restarts with retained external state, and verifies exact resource identities and creation counts.
- **important — F9: the archive test does not verify channel preservation in Discord.** `src/test/java/com/discordtowny/space/DefaultSpaceServiceTest.java:406` and `:416`. The gateway is a success-only mock, so checking stored IDs and absence of a submitted `DeleteSpace` cannot detect deletion inside the `ArchiveSpace` executor. The test also never verifies the claimed channel movement, read-only permissions or role removal. The fix must exercise that operation's implementation and verify no text/voice deletion, correct archive placement/access, and removal of the town role; keep the existing assertions as service-level checks only.
- **important — F10: exact restore assertions still only verify a hand-written substitute.** `src/test/java/com/discordtowny/space/DefaultSpaceServiceTest.java:458` and `:481`. This test does use exact equality, not `contains`, but its mock explicitly writes the original channel IDs and the replacement role. It would pass if the real executor created extra channels or skipped restoration entirely. The fix must exercise the real restoration flow and assert exact retained Discord channel IDs, zero channel-creation/deletion calls, restored placement/permissions, and role assignments, including a failed-operation case. The existing executor test at `src/test/java/com/discordtowny/discord/JdaGuildOperationExecutorTest.java:644` checks a saved role, not these restoration postconditions.

## Boundaries and acceptance evidence

No direct JDA/Bukkit imports or Towny reads were found in the service. Its Discord mutations all go through `submit`; creation checks availability/permissions off the supplied executor. Rename/archive/restore reject unsuccessful operation outcomes rather than silently completing successfully, and purge counts only successful deletions. No channel-deletion path outside the purge-submitted `DeleteSpace` was found. Restoration normally reuses saved channel IDs; F5–F7 concern cases where that normal path is incomplete or unreachable.

The current service deliberately relies on its caller for main-thread mayor verification and administrator authorization of purge. The repository has no create/delete command adapter or production construction of `DefaultSpaceService`; the plugin entry point remains a skeleton. The T6 card lists `/dt create` and confirmed `/dt delete`, while the plan also assigns command work to Phase 5. This is an explicit integration/scope dependency for the architect to resolve, not grounds to invent a new authorization mechanism in this service or claim that command acceptance has passed. The eventual mayor delete command must archive, and permanent deletion must remain administrator-confirmed.

No optional cleanup or stylistic debt is included. Required corrections are F1–F10: safe crash recovery and ownership, atomic admission, correct failure classification, complete lifecycle recovery/restoration, and tests that execute the behavior rather than supplying it. Cross-package fixes and command-scope ownership need architect coordination before declaring T6 complete.

Final verdict: needs corrections
