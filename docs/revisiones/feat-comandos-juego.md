# T8 review: feat/comandos-juego

Static review of the T8 card (including both inherited blocks), specification sections 4 and 9.1, governing architecture, production wiring, command adapters, and their tests. No git or Gradle commands were run. The green build and 426 tests are the architect's reported results, not executions performed for this review.

- **blocking** — `src/main/java/com/discordtowny/DiscordTownyWiring.java:119`: `start()` is called directly from `DiscordTownyPlugin.onEnable()` and synchronously initializes Hikari and runs SQL migrations. An unreachable database therefore blocks the server thread through connection timeouts before degradation occurs; even healthy startup executes database queries there, contrary to P4 and architecture section 3. The fix must initialize persistence off the main thread, preserve the database-before-Discord gate, and safely return to the server thread for registration without allowing a late startup completion after disable.
- **blocking** — `src/main/java/com/discordtowny/minecraft/MinecraftCommands.java:155`: the new `help.*` and `status.*` keys, and most new admin keys such as `admin.list-entry`, `admin.info-header`, `admin.purge-empty`, and `admin.reload-failed`, exist in neither bundled message catalog. Fresh installations show `[missing message: ...]` instead of command instructions and results in both languages and in the console. The fix must coordinate the required catalog additions with the resource owner and verify all new command keys against real English and Spanish catalogs. The mocks at `src/test/java/com/discordtowny/minecraft/MinecraftCommandsTest.java:82` manufacture a response for every key and conceal this failure.
- **important** — `src/main/java/com/discordtowny/DiscordTownyWiring.java:260`: reload replaces only the wiring's configuration reference; the gateway, space/link/sync services, and player-join listener retain the original immutable configuration, and the periodic job is not rescheduled. For example, switching from REPAIR to REPORT reports the new mode in command replies while the service continues mutating Discord in REPAIR mode; changing the interval or link expiration likewise leaves the old behavior active. The fix must apply supported reload settings consistently to their consumers and reschedule the job, with explicit handling for settings that require restarting and for recovery from degraded startup.
- **important** — `src/main/java/com/discordtowny/DiscordTownyWiring.java:139`: the asynchronous connection future is discarded. If disable occurs while `JdaDiscordGateway.doConnect()` is waiting at `src/main/java/com/discordtowny/discord/JdaDiscordGateway.java:112`, `stop()` can shut down an apparently empty gateway and close storage, after which the connection thread publishes JDA, starts queues, and marks itself available. This leaves a live Discord client after plugin shutdown, backed by closed persistence. The fix must coordinate connection completion and shutdown so an in-flight start cannot publish resources after stop, and close resources acquired during that race; this requires coordination with the Discord package owner.
- **important** — `src/main/java/com/discordtowny/DiscordTownyPlugin.java:28`: the main-thread executor silently accepts and discards work once the plugin is disabled. `DefaultSyncService.callTowny()` wraps this executor in `CompletableFuture.supplyAsync` (`src/main/java/com/discordtowny/sync/DefaultSyncService.java:750`), so an in-flight reconciliation reaching a Towny read during shutdown remains incomplete forever. Cancelling already queued Bukkit tasks at `src/main/java/com/discordtowny/DiscordTownyWiring.java:213` has the same completion problem. Avoiding Towny access during shutdown is correct, but silent loss is not cancellation. The fix must terminate affected futures explicitly and coordinate outstanding domain work before closing its dependencies, without executing Towny reads on a worker thread or blocking the server thread waiting for itself.
- **important** — `src/main/java/com/discordtowny/minecraft/MinecraftCommands.java:973`: the new player `/dt sync` report formatter returns before reporting problems in REPORT mode and whenever any repair or role change succeeded. It also prints `sync.finished` when inconsistencies remain unrepaired but the problems list is empty. A partially failed reconciliation can therefore look successful, unlike the existing admin formatter in `SyncMinecraftCommands`. The fix must preserve problems and unrepaired counts for player synchronization in both modes, including mixed success/failure reports.
- **important** — `src/main/java/com/discordtowny/minecraft/MinecraftCommands.java:803`: new user-visible diagnostics are hard-coded English, including missing-channel/role explanations and deleted/ruined-town explanations; list output also supplies English `text`, `voice`, and `none` values at line 697, and creation failure supplies `Internal error` at line 492. With `language: es`, translating the enclosing message cannot translate these inserted values. The fix must resolve human-readable values and diagnostics through the selected player catalog while retaining English console output; IDs and timestamps need no translation.
- **important** — `src/test/java/com/discordtowny/minecraft/MinecraftCommandsTest.java:114`: every unified-command test uses an inline scheduler and precompleted operation futures, so these tests cannot detect a completion handler replying directly on a worker thread. Admin tests invoke command callbacks directly, bypassing Brigadier permission enforcement, and the reload test merely verifies a mock Runnable was called. The fix must add focused checks using delayed futures and a queued scheduler, exercise permission rejection through the command tree, and verify actual wiring reload behavior. These are gaps in the claimed coverage, not evidence that the currently inspected callbacks bypass their scheduler.
- **minor** — `src/main/java/com/discordtowny/minecraft/MinecraftCommands.java:865`: the first `/dt admin purge` invocation queries storage asynchronously without an immediate acknowledgement. With slow storage the command is silent until the confirmation/count query completes, contrary to T8's immediate-response requirement. The fix must acknowledge before starting that query while preserving explicit confirmation before deletion.

Review conclusions on the requested risk areas: failed initial database setup closes and clears storage and prevents constructing the gateway or domain services; an invalid token leaves the gateway unavailable through its asynchronous connection handler. Missing Towny is rejected by the required server dependency in `paper-plugin.yml`. The periodic job is started and stopped; validated intervals are integer minutes bounded by `Integer.MAX_VALUE`, so the seconds-to-ticks multiplication fits in a long, and a zero interval is rejected by the job before scheduling. Player admin help filtering and the actual admin command node both use `discordtowny.admin`. The production unified console paths select English messages, while player paths use configured messages; the missing catalogs and hard-coded values above remain separate defects. Inspected asynchronous command success/error replies use the injected scheduler rather than directly sending from the completion thread.

Shutdown test assessment: `DiscordTownyPluginTest.java:99` uses Mockito `InOrder`, so it proves periodic-job, gateway, and storage invocation order, not merely that each was closed. The storage-only and gateway-plus-storage throwing cases exercise populated partial states and continuation after failure. The job-only case at line 31 is not a state reachable through the current construction order. None of these tests actually drives a failing `start()`, an in-flight connection, scheduler cancellation, or outstanding service work; call order does not prove asynchronous resource termination. The JavaPlugin testing limitation is accepted, but its executor and scheduler lambdas contain meaningful lifecycle policy, as the shutdown finding demonstrates.

Integration dependency, not an additional T8 blocker: no production caller constructs/registers the existing `LinkSlashCommands` listener or publishes its command definitions. A generated `/dt link` code cannot yet be redeemed through this runtime. Coordinate this with T9's Discord registration work before server acceptance; this is distinct from the accepted English slash-command metadata debt.

Final verdict: needs corrections
