Scope: `9db5593..300c41e`. Verdict: **blocked**.

## Findings

**F7 — A prefix can be saved without an audit event during startup.** `DiscordTownyPlugin.java:82-86` supplies an audit consumer that silently returns while `wiring.getAuditSink()` is null. `DiscordTownyWiring.java:223` publishes storage, making `getSettingsRepository()` available, but installs the audit sink only at `:264`, after Discord gateway setup. The command is already registered before `wiring.start()`. A permitted `/dt admin prefix ...` in that interval can write the setting, apply it, and report success while producing no audit row. Make availability of settings and audit delivery move together, or refuse the change when auditing is unavailable; verify that a successful command cannot silently skip the required audit.

**F8 — Failure after a successful write is reported as a database failure.** In `MinecraftCommands.java:1690-1713` and `:1770-1795`, `settings.delete`/`put` completes before `auditConsumer.accept`, then the in-memory `resetPrefix`/`setCustomPrefix` runs in `thenRun`. The final `exceptionally` covers all of these stages and always sends `general.database-unavailable`. If audit delivery throws, the database has changed but the old prefix stays live and the operator is told the write failed; restart or reload reveals the supposedly failed change. If applying the value throws, the database has again changed and the same false answer is sent. The production `CompositeAuditSink.accept` normally contains its own dispatch errors, so the first case needs an exceptional audit consumer; the command API permits one, and the error path makes no distinction. Separate write failure from later failures, and make the operator's reply describe the persisted state accurately.

## Checks

- **Production route:** `DiscordTownyPlugin.register` passes live suppliers and the audit consumer to `MinecraftCommands.register`, which passes them to `createCommandNode`. For a player, `resolveMessages` obtains `wiring.getMessages()`. Wiring holds `YamlConfigLoader.messages()`, whose `ReloadableMessages` explicitly delegates prefix mutation and `get` to the current `YamlMessages`. Startup and reload read the stored value into that wrapper. Apart from F7, the value reaches subsequent player messages; `plain()` retains the catalog prefix for console and Discord. No reflective lookup remains in production source.
- **Write ordering:** Failed `put`/`delete` does not apply the new value or write the audit event. Successful writes are followed by audit dispatch, in-memory apply, then the success reply. F8 is the later-failure case.
- **Component split:** `get` resolves placeholders in the body once, then appends separately deserialized prefix and body components. The prefix's colours and literal trailing space remain; its trailing `&r` contributes no visible character, while the body starts with its own style, so unclosed prefix formatting cannot bleed into it. `plain` likewise combines once before plain serialization. Existing placeholder behavior is retained; there is no second deserialize of the combined text.
- **Limits:** `visibleLength` plain-serializes the same legacy prefix format used to render, then counts Unicode code points, with a 32-visible-character refusal. The separate 255 UTF-16-unit raw cap has its own refusal. A final `&` and `&&` are not complete formatting codes, so they remain visible and consume the visible budget. The count is characters, not pixel width; the task report states this ceiling.
- **Warning order:** Before this diff, Java evaluated `catalogPrefix() + text(key)` and `effectivePrefix() + text(key)` left to right. The new `get` and `plain` assign the prefix before evaluating `text(key)`, restoring the warning order for missing keys without changing the pre-existing test. Other callers of `get` and `plain` still obtain prefix then body; `label` is unchanged. The only rendering-order difference is the intended formatting boundary between prefix and body.
- **F6:** The scope decision holds. The constitution excludes multi-server networks, and `docs/spec.md` §9.1 explicitly describes the shared-database lag and reload synchronization point. No supported deployment requires cross-instance immediacy. A read per chat message would also conflict with the main-thread database rule.
