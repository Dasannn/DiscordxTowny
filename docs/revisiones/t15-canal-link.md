**Blocking**

For an absent key, `text` records `discord.link-channel-id: expected quoted text if it is a number` (lines 204–207). Returning an empty string afterwards does not remove that error: `load()` throws at lines 87–88. Existing installations without this new key therefore enter degraded mode through `DiscordTownyWiring.start():104–109`; the loader reads the disk file without merging bundled defaults. Reproduction: take a valid configuration, remove only `discord.link-channel-id`, and load it. Required outcome: absence and explicit `""` must both load as unrestricted, while explicitly invalid values still fail with the exact key. Add a regression using an existing configuration with the key removed; copying the new bundled configuration cannot exercise this case.
- **B2 — Inherited integration blocker, not introduced by T15.** `src/main/java/com/discordtowny/discord/JdaDiscordGateway.java:98–112` builds JDA without either slash-command listener; `DiscordTownyPlugin.java:52–62` registers only Minecraft synchronization listeners. A search of all `src/main` finds no instantiation of `LinkSlashCommands` or `TownySlashCommands`, no `addEventListener`, and no slash-command registration call. The same absence exists on `main`. A fresh installation cannot expose these commands through this code, and preexisting Discord registrations would have no handler. Required outcome, owned by the architect/integration task: wire and register the adapters so real interactions reach them before claiming live T15 acceptance. Include configuration refresh in that integration: `LinkSlashCommands.java:35,42` captures a final snapshot, while `DiscordTownyWiring.reload():344–454` replaces the wiring's config and domain services without updating/replacing a slash listener or warning that its channel restriction requires restart. A retained listener would keep allowing the old channel after a successful reload. Do not expand the T15 author's exclusive zone to fix the wiring without coordination.

**Acceptance and requested edge cases**

1. **Empty versus absent:** explicit `link-channel-id: ""` becomes `Optional.empty()` and skips the new block for both `/link` and `/unlink`; the previous enabled-command, cooldown and handler behavior remains. Absence fails B1. Numeric YAML values are rejected as unquoted text; whitespace is deliberately rejected rather than treated as empty.
2. **Only linking commands:** `LinkSlashCommands.onSlashCommandInteraction():77–81` returns for every name except `link` and `unlink`, before reading the setting or replying. `/town`, `/res`, `/residents`, `/townlist`, `/mytown` and `/help` are therefore unaffected by this guard. `TownySlashCommands.java:186–239` independently dispatches those six commands and never reads `linkChannelId`. This is source-level adapter evidence, subject to B2 for live operation.
3. **Private refusal and correct destination:** lines 99–102 pass exactly `{channel: "<#" + allowedId + ">"}` to `linking.wrong-channel`, then call `reply(...).setEphemeral(true).queue()`. This does not depend on the command's configurable visibility. For a valid destination the mention identifies its configured ID; I1 covers destinations that cannot be used.
4. **A refused code stays valid: yes, by the actual guard order.** Command-name filter → enabled-command check → channel refusal and immediate return → user/cooldown lookup and update → link/unlink handler. The refusal neither reads the code option nor defers into `handleLink`; it never invokes `LinkService.redeem`. `DefaultLinkService.redeem():132–218` contains the repository consumption and failed-attempt tracking, so neither can run on this path. `userCooldowns.put` is below the return, so no new cooldown begins. `/unlink` likewise never looks up the account or removes it on refusal. A preexisting cooldown/lockout still applies, and ordinary code expiration continues; refusal does not extend validity.
5. **Fallback reachability:** the fallback is dead for valid current slash-command events, not a remedy for a missing cached channel. The installed dependency is JDA 6.6.0. Read-only `javap -c` inspection confirms that `Interaction.getChannelId()` converts `getChannelIdLong()` to an unsigned string, returning null only for zero; `GenericInteractionCreateEvent` delegates that ID to the interaction, and `InteractionImpl` reads the payload's `channel_id` independently of the channel object. The general interface allows a future context-free interaction, but that is not a current slash event with a usable channel. See the [JDA Interaction contract](https://docs.jda.wiki/net/dv8tion/jda/api/interactions/Interaction.html) and [slash-command channel contract](https://docs.jda.wiki/net/dv8tion/jda/api/interactions/commands/SlashCommandInteraction.html). The test creates the inconsistent null-ID/non-null-channel state itself. This is **minor implementation debt**; it does not justify an additional blocker.
6. **Threads:** the event carries the thread's own ID, not its parent's ID. Discord defines a separate thread `id` and `parent_id`; JDA also builds a thread channel for thread interactions. Consequently a thread inside the configured parent is refused and the reply points to the parent. Configuring the thread ID itself would admit that thread. This matches a literal reading of spec 5.1.1's “only in that channel”; the spec grants no descendant-channel exception. Treat parent-plus-threads behavior as a requirement change, not an assumed bug fix. This interpretation follows the [Discord thread fields](https://docs.discord.com/developers/topics/threads#thread-fields).
7. **Three-argument constructor:** the `PluginConfig.Discord` convenience constructor is at `PluginConfig.java:62–64`. Old callers still compile but silently construct an unrestricted configuration. Reconstructing an existing restricted configuration with only token, guild and log ID would discard its restriction, and old test fixtures never force their authors to consider the new field. Current production construction is exclusively the updated four-argument loader; the remaining three-argument uses found are tests. This is **not evidence of a current production bypass**, and it does not fix absent YAML support. Preserve the field in any configuration-copy path; keep intentional unrestricted fixtures explicit.
8. **Minecraft colors in Discord:** `YamlConfigLoader.ReloadableMessages.plain():174–175` delegates to `YamlMessages.plain():67–68`. That calls `get`, which deserializes ampersand formatting from the prefix and message, substitutes placeholders as literal components, then serializes plain text. Thus `&c` is stripped rather than displayed or rendered red; `<#ID>` survives. With the English defaults the outgoing text is `[DiscordTowny] This command can only be used in <#ID>.` `plain` includes the prefix; `label` is the prefix-free accessor. This is a chat refusal, not an embed/button label, so the chosen accessor is appropriate.
9. **Catalog parity and order:** both catalogs add exactly `linking.wrong-channel` at line 36, with exactly `{channel}` and quoted scalar values. Each entry is appended to the existing `linking` mapping after `link-required`; no existing key is reordered or rewritten. Neither new key is a YAML 1.1 boolean/null token. Existing on-disk catalogs lack the key until updated; the existing loader falls back to bundled English and warns once, as spec 9.1 requires.
