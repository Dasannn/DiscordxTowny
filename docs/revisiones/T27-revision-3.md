## Findings

- **F6 — named follow-up — the stale-cache loop still exists on prolonged gateway failure.** The new catches return `TRANSIENT_FAILURE` (`JdaGuildOperationExecutor.java:368-400`). If a deleted source remains in JDA's cache and each move returns `UNKNOWN_CHANNEL`, all attempts take that path. `GuildOperationQueue.java:190-204` retries with backoff, then calls `onOperationFailed` at line 197; `JdaGuildOperationExecutor.java:1069-1070` marks the row `INCONSISTENT`. Sync archives ruined or deleted towns whenever their space is not `ARCHIVED` (`DefaultSyncService.java:499-520`, also lines 251-260 and 454-463), so the next periodic run repeats it. This is the old loop with several attempts per cycle, not guaranteed convergence. While it persists, the operator sees move warnings and queue retry/exhaustion logs, a failed `space_archive` audit event in the Discord log, an inconsistent space, and a sync problem. `/dt admin purge` reports the inconsistent space as skipped; it cannot clear it. Once JDA learns that the source is absent, the next attempt can archive and emit the success note. Follow up with a bounded, authoritative way to resolve a source that remains cached, or explicitly require operator intervention after exhaustion. Do not describe backoff alone as settling the truth.

- **F7 — named follow-up — a vanished destination is retryable but not covered by the round-4 null guard.** `ensureCategoryWithCapacity` can return a category at `JdaGuildOperationExecutor.java:346`, and Discord can delete it before `setParent(...).complete()` at line 356 or 381. The null guard at lines 347-352 cannot detect that race. The new catch correctly avoids saving `ARCHIVED`; on a later attempt `ensureCategoryWithCapacity` may find or create a usable category. If the cache keeps returning the deleted category, the same `UNKNOWN_CHANNEL` path reaches F6's exhaustion and sync loop. The return value of `ensureCategoryWithCapacity` is not evidence that the category remains live. A focused destination-deleted-after-lookup test and recovery policy belong in the follow-up.

- **F8 — named follow-up — partial retry is plausible, but its safety is not tested.** The role is deleted before either channel move (`JdaGuildOperationExecutor.java:326-341`). A text move and its permission changes can succeed before the voice move returns early at lines 379-400. The row is still unarchived, with its old role ID and channel IDs. On retry, a missing role is skipped, or a stale role lookup followed by `UNKNOWN_ROLE` is treated as absent; the text and voice moves and permission overrides are repeated, then the row is saved `ARCHIVED` only after both complete. Repeating those Discord updates is intended to be idempotent, and no duplicate channel is created by this path. If the destination disappeared, the retry can select another archive category and move the text again. This is recoverable when Discord and the cache become usable, but it is not atomic and can remain half-done through retry exhaustion. The tests exercise one channel becoming absent on the second attempt; none exercises role deleted plus text moved plus voice failure followed by retry. Add that one scenario to the follow-up, including final parent and permissions, to substantiate the safety claim.
