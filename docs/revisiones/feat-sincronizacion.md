# T7 review: feat/sincronizacion

Static review against the T7 card, constitution, specification sections 4, 6 and 7, acceptance criteria 4, 5, 6 and 8, and the architecture's threading rules. Reviewed the synchronization service, three Minecraft adapters, `roleHolders` contract/implementation, their tests, and the existing collaborators needed to trace execution. No git, Gradle, or tests were run. The architect reports a green build with **351 tests**; that is external verification, not this reviewer's execution. Only this report was written.

## Findings

1. **blocking — Deleted Discord resources with persisted IDs are not detected.** `src/main/java/com/discordtowny/sync/DefaultSyncService.java:443`: the missing-resource checks inspect only whether database IDs are absent. Manually deleting a text channel, voice channel, or town role leaves its ID present, so an otherwise healthy ACTIVE space never dispatches repair. `roleHolders` returning empty does not distinguish a deleted role from an empty cache and does not repair it. The executor can check actual channel existence inside `CreateSpace` (`src/main/java/com/discordtowny/discord/JdaGuildOperationExecutor.java:125`), but this path never invokes it. **Fix should achieve:** read-only verification of registered resources against Discord, accurate report-mode detection, and confirmed repair in repair mode. Coordinate any gateway contract addition with the architect. A regression must retain the database ID while making the Discord resource absent; substituting an empty database ID does not test acceptance criterion 6.

2. **blocking — Lifecycle repair can reopen a ruined town, and failed deletion archives stop being retried.** `src/main/java/com/discordtowny/sync/DefaultSyncService.java:375`, `:425`, `:448`, and `:345` (also `:221`): lifecycle branches are independent and use the original space state. A ruined ACTIVE space with no registered role but intact channels queues both `ArchiveSpace` and `CreateSpace`; creation recreates access, assigns residents, and marks the space ACTIVE. A ruined INCONSISTENT space without `archivedAt` also goes straight to creation. Conversely, once an archive for a deleted town fails and the executor marks its space INCONSISTENT, subsequent passes skip archiving because they accept only ACTIVE spaces. **Fix should achieve:** one lifecycle decision consistent with current Towny state, no creation/grants for ruined or deleted towns, and retriable incomplete archives. Consume the existing space lifecycle service where appropriate; its archive path records intent before submission (`src/main/java/com/discordtowny/space/DefaultSpaceService.java:259`). Test the resulting state and permissions, not just successful mock outcomes.

3. **blocking — Failed Towny reads can be treated as proof that access must be removed.** `src/main/java/com/discordtowny/sync/DefaultSyncService.java:150`, `:214`, and `:340`: `isAvailable()` succeeding does not certify that the following lookup succeeded. `LiveTownyFacade.read` catches runtime/read failures and returns the same empty value used for absence (`src/main/java/com/discordtowny/towny/LiveTownyFacade.java:68`). A snapshot failure can therefore archive a living town; failed resident/town lookups can revoke a linked resident's managed roles. This is separate from the Discord holder lookup, whose empty/exception handling is conservative. **Fix should achieve:** distinguish confirmed absence from failed reads before destructive reconciliation, report failures without changing access, and preserve genuine deletion/no-town handling. This requires architect coordination with the existing facade contract; another availability check alone cannot prove a snapshot read succeeded.

4. **important — Revived archived spaces are never restored.** `src/main/java/com/discordtowny/sync/DefaultSyncService.java:365`: an ARCHIVED space whose town is now alive and not ruined falls through without restoration; residents and holder auditing are restricted to ACTIVE spaces. No synchronization path calls `SpaceService.restore` or submits `RestoreSpace`. An INCONSISTENT restoration carrying `archivedAt` is instead sent back to archive at `:414`. **Fix should achieve:** recognize revival and resume restoration with history intact, including the documented same-name recreation case, using the existing lifecycle operation. Verify an archived-to-active transition and restored resident access rather than only dispatch.

5. **important — Main-thread dispatch is optional even though the live facade requires it.** `src/main/java/com/discordtowny/sync/DefaultSyncService.java:559`: constructors at `:87`, `:110`, and `:120` allow no main-thread executor, and `callTowny` then executes every Towny read on the worker pool. Using these public overloads with `LiveTownyFacade` fails at its thread assertion. With a correctly supplied scheduler, the service's Towny calls are inside `callTowny`, and database/Discord continuations use the worker executor. A related ordering defect exists at `src/main/java/com/discordtowny/minecraft/SyncMinecraftCommands.java:153`: suggestions call `isAvailable()` before checking `Bukkit.isPrimaryThread()` and outside the catch, so the guard cannot protect an off-thread invocation. **Fix should achieve:** make correct main-thread dispatch mandatory for live service construction and guard/schedule every facade call, including availability. The test at `src/test/java/com/discordtowny/sync/DefaultSyncServiceTest.java:646` only records that an executor was called; its executor runs inline on the worker. Use distinct controlled execution contexts and assert the context of each facade call and repository/Discord access.

6. **important — The periodic reconciliation job is missing.** `src/main/java/com/discordtowny/sync/DefaultSyncService.java:253`: `reconcileAll` is a one-shot operation. Production sources contain no consumer of `config.sync().interval()`, no repeating synchronization task, and no start/stop lifecycle for such a task; its production caller is the administration command. Thus a manually granted role will not be removed by the promised next periodic pass. **Fix should achieve:** provide the configured periodic job, shutdown handling, and observable pass results, with architect-owned bootstrap wiring explicitly coordinated. This finding concerns the T7 job requirement, not a request for the author to implement all unfinished plugin bootstrap wiring.

7. **important — One failed space aborts later batches and discards the accumulated report.** `src/main/java/com/discordtowny/sync/DefaultSyncService.java:311` and `:286`: a repository exception in one space makes its future exceptional, so `allOf(...).thenApply(...)` never merges results and later batch continuations never run. An exception from a Towny supplier has the same effect. The overall future fails visibly, but it supplies neither the partial report nor which later spaces were skipped. Ordinary unsuccessful `OperationOutcome` values are handled and do not cause this problem. **Fix should achieve:** retain per-space failures and completed results, continue independent spaces/batches where safe, and explicitly report any deliberate pass-wide abort. Test a failing space followed by work in a later batch.

8. **important — Commands discard failures and report-only notices carried by successful futures.** `src/main/java/com/discordtowny/minecraft/SyncMinecraftCommands.java:110`, `:141`, and `:179`: every normally completed `SyncReport` produces only `sync.finished`. The service deliberately returns reports containing Towny-unavailable errors, failed Discord outcomes, missing spaces, and holder-lookup failures without throwing. None of those reaches the sender, and a report-only pass hides all its detected problems as well. The command failure tests supply exceptional futures, bypassing the normal outcome path. **Fix should achieve:** inspect and present the report, distinguishing completed repairs, unresolved failures, and report-only findings; do not imply that synchronization succeeded merely because its future completed. Test a normally completed report containing failed operations and a report-mode report containing discrepancies. Coordinate missing message keys with their owner.

9. **important — Role counts describe requested sets rather than actual changes, and report mode misses missing assignments.** `src/main/java/com/discordtowny/sync/DefaultSyncService.java:614`, `:487`, and `:525`: the so-called diff is all desired roles plus all other managed roles, without reading current membership. The executor correctly skips already-held grants and absent revocations, but the report counts their full requested sizes anyway. A fully synchronized resident can therefore produce nonzero grants/revocations on every pass. In REPORT mode the resident diff is discarded at `:481`; if Alice holds the town role and Bob should hold it but does not, the nonempty holder sweep finds no intruder and Bob's missing assignment goes unreported. Separately, `:526` increments `rolesRevoked` for a hypothetical revocation despite `SyncReport` carrying no mode. **This is misleading enough to matter:** the same field can mean attempted changes, actual holder revocations, or changes that never happened. **Fix should achieve:** detect actual membership discrepancies, keep confirmed changes distinct from proposed changes, and label report-only results unambiguously. Include an already-correct no-op pass and a missing-role report pass. The test at `src/test/java/com/discordtowny/sync/DefaultSyncServiceTest.java:498` asserts requested-list sizes against an unconditional success stub, so it does not establish its claimed “real counts.”

10. **important — Join-triggered synchronization writes to the database in report mode.** `src/main/java/com/discordtowny/minecraft/PlayerJoinSyncListener.java:67`: the listener always calls `updateLastKnownName` before `syncPlayer`, regardless of synchronization mode. The service's report-mode guard at `src/main/java/com/discordtowny/sync/DefaultSyncService.java:159` therefore does not protect this entry point. A linked player joining while REPORT is configured changes persistent state. **Fix should achieve:** keep this synchronization entry point mutation-free in report mode and test the listener together with the report-mode policy, asserting zero writes and zero submissions. The direct reconciliation report test does not exercise this path.

11. **important — Unjustified global mayor-role holders are outside the reconciliation sweep.** `src/main/java/com/discordtowny/sync/DefaultSyncService.java:502`: only each active town's role is enumerated. Resident synchronization corrects mayor roles for linked residents of active spaces, but an unlinked user, a linked townless player, or a former mayor outside those resident lists can retain a manually granted/stale mayor role indefinitely. Town-role auditing revokes only that town role and never evaluates the mayor role. **Fix should achieve:** reconcile holders of the managed global mayor role against verified links and live mayorship, including holders outside active-space resident lists; preserve unrelated roles and do not revoke on failed reads. Cover legitimate mayors whose town has no registered space as well.

12. **minor — The batching test does not prove the advertised boundaries.** `src/test/java/com/discordtowny/sync/DefaultSyncServiceTest.java:486`: the assertions accept `process, process, pause, pause, process, process, process`. They prove two pauses, neither at an endpoint, but not that two spaces finish between pauses. Events are recorded at Towny lookup, with all continuations running inline, so the test also does not establish that pending Discord work completes before the next batch starts. **Fix should achieve:** assert the exact batch boundary sequence and hold an operation future pending to prove the pause/next batch waits. The implementation's happy-path ordering at `DefaultSyncService.java:286` is correct; this is test debt, not a claim that its normal pauses are misplaced.

## Checked behavior and test limits

- **Role scope:** for a linked ordinary resident, the desired set contains their town role; a mayor additionally gets the managed mayor role. A player with no town has no desired roles; an unlinked UUID submits nothing. A player whose town has no space receives no town role, while a verified mayor may still receive the global distinction. The generated revocations are restricted to managed IDs, and the existing executor independently filters managed roles and uses individual add/remove operations rather than replacing the whole role set. Findings 2, 3, 9 and 11 concern lifecycle, failed-read, measurement, and coverage gaps around this normal behavior.
- **Holder sweep:** empty/throwing Discord lookups do not turn into revocations. The justification set is built before holder revocations, so a thrown link-repository lookup also prevents sweep revocations. With a successful nonempty lookup, a holder absent from the linked-resident set is not skipped merely because they have no account link. The test at `src/test/java/com/discordtowny/sync/DefaultSyncServiceTest.java:862` compares Bob's revoke list exactly to the single audited town role and checks an empty grant list. This proves the operation's scope; it does not compare a simulated final member-role set. Existing executor tests additionally verify that external-role removals are never submitted. Do not describe the service mock as an end-to-end proof of final Discord membership.
- **Report tests:** `src/test/java/com/discordtowny/sync/DefaultSyncServiceTest.java:398` explicitly verifies zero submissions and checks space/link write methods at `:402` through `:410`; it is stronger than a report-counter assertion. It does not exhaust every repository mutator, and its towns have no residents. The separate holder report test at `:932` checks zero submissions but no repository-write assertions. Neither covers the join listener's unconditional write. Extend coverage to the concrete paths in findings 9 and 10, rather than treating the existing test name as proof of all report-mode behavior.
- **Listeners and waiting:** the Towny wrappers extract UUIDs/names and delegate. No listener waits on a dispatched future. Their unfinished-future test exercises delegation without manufacturing completion. Player-join database work is dispatched asynchronously by the production registration path. `processBatch` joins only after `allOf` has completed. These observations support nonblocking listener behavior; no live tick-performance test was run.
- **Accepted limit:** extraction inside Towny's `@EventHandler` wrappers remains untested because Towny objects cannot initialize in this Mockito environment. The wrappers are thin; this settled limitation is not a finding. Thread-test weaknesses in finding 5 concern testable executor boundaries, not those wrappers.

## Verdict

Integration requires live Discord resource detection/repair; safe, retriable archive and restoration decisions; failed-read/absence distinction; mandatory Towny thread dispatch; the periodic job; isolated batch failures; visible and truthful reports; mutation-free report-mode joins; and global mayor-holder reconciliation. Regression checks must exercise these outcomes rather than merely return successful dispatch results. Finding 12 is nonblocking test debt. Cross-package contract and bootstrap work must be coordinated with the architect rather than performed outside the author's zone.

Final verdict: needs corrections
