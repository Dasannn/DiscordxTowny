# T9 review: feat/comandos-discord

Static review of `TownySlashCommands.java`, its test, the facade and snapshot implementations, and the five governing documents. Git and Gradle were not run. The green build and 424 tests were reported by the architect, not executed by this reviewer.

## Findings requiring correction

- **blocking** — `src/main/java/com/discordtowny/discord/TownySlashCommands.java:267` (also 307, 340, 400, 440, 480, 535): `callTowny` completes on the server main thread, but its non-async `thenAccept` and exceptional continuations do not hand execution back to an off-main executor. When the scheduled read completes after these callbacks are attached, embed construction and `hook.editOriginal*().queue()` execute on the main thread, violating architecture section 3/P4. Keep Towny reads on main and explicitly dispatch both successful replies and failure replies off main. `src/test/java/com/discordtowny/discord/TownySlashCommandsTest.java:84` executes the task inline, and the assertion at 829 merely counts submissions; replace that proof with a delayed executor/thread-aware check that rejects Towny outside main and Discord work on main across slash and button paths.
- **important** — `src/main/java/com/discordtowny/discord/TownySlashCommands.java:244` (also 326, 361, 422, 462, 503): linking is required before even checking whether an explicit target was supplied. Unlinked users cannot use `/town <name>`, `/res <resident>`, `/residents <town>`, or `/townlist`; a database outage also disables these identity-independent reads. Spec 5.1 explicitly allows information queries without linking; spec 5.2 protects viewing/typing in private town channels, not all town information. Restrict identity lookup to commands that need the author's Minecraft identity, preserve private-channel permissions, and correct the tests at `src/test/java/com/discordtowny/discord/TownySlashCommandsTest.java:250` and 302 that currently enforce the broader restriction. If universal linking is intended instead, the architect must resolve that requirements conflict before integration.
- **important** — `src/main/java/com/discordtowny/discord/TownySlashCommands.java:206`: button interactions bypass the command activation and cooldown checks at 164–185. Existing buttons can continue reading Towny even when the associated command is disabled, and repeated clicks can trigger full town/resident scans without the configured delay. Apply the relevant command settings to pagination interactions before starting reads, acknowledge rejection promptly, and test disabled-command and repeated-click cases.
- **important** — `src/main/java/com/discordtowny/discord/TownySlashCommands.java:714` (also 639, 656, 684, 688, 718–741): help content, list titles, empty-list text, and the last-online label are hard-coded English. With `language: es`, these response embeds remain partly or entirely English, violating spec 9.1 and acceptance criterion 12. Route response text through `Messages`, reuse `embed.last-online`, and report the missing catalog entries to the configuration owner. The accepted English Discord registration metadata exception does not cover response embeds. Tests at `src/test/java/com/discordtowny/discord/TownySlashCommandsTest.java:565` and 795 currently assert the hard-coded titles and should instead verify catalog use.
- **important** — `src/main/java/com/discordtowny/discord/TownySlashCommands.java:570` (lookup at 511): resident pagination stores the town name as its identity. If a town is renamed between clicks, the next page reports it missing; if another town takes the old name, it silently switches to that different town. Architecture section 5 explicitly requires town UUID identity because names change. Carry the stable town UUID through pagination and resolve fresh snapshots by UUID, including a rename/name-reuse regression check.

## Noted debt

- **minor** — `src/main/java/com/discordtowny/discord/TownySlashCommands.java:464` (also 505): any unlinked viewer of a public response can press a button, overwrite the shared response with their own linking error, and remove its navigation for everyone. Shared pagination by another eligible viewer is not itself a private-channel access leak, but actor-specific rejection should not destroy someone else's response. Send that rejection privately to the clicker while preserving the existing message and controls.
- **minor** — `src/test/java/com/discordtowny/discord/TownySlashCommandsTest.java:627` (also 675, 710): resident pagination checks the page count and a few labels, and button tests check only the footer. They do not establish the final page's exact items, disabled-next state, clamping of out-of-range requests, or behavior after growth/shrinkage/deletion between clicks. Town-list tests at 545 and 585 do verify first/second-page item boundaries, so this is incomplete coverage rather than wholly artificial pagination testing. Add focused checks using changed facade results and the actual resulting items and controls; the current clamping arithmetic itself appears correct.

## Other acceptance checks

All facade calls, including the availability probe and nested mayor/resident lookups, are inside `callTowny`. The live facade copies names, UUIDs, scalar values, and resident UUID lists; no live Towny object escapes. The thread defect above concerns the response continuation, not an off-main Towny read.

Supported slash commands defer before database or Towny work. Disabled-command and cooldown paths use immediate replies instead of deferral and perform only in-memory checks; they already acknowledge the interaction without slow work. Valid pagination buttons defer before reads. No pre-acknowledgement large-town scan was found.

Confirmed absence and `TownyReadException` lead to distinct message keys, with early returns before embed rendering. The missing-town test at 316 and failure test at 397 explicitly verify that `editOriginalEmbeds` is never called; their key-returning message substitute is intentional and does not fabricate that behavior. No data-command path was found claiming success without first reading Towny; `/help` legitimately needs no Towny read.

Fresh lists are read for each page and page numbers are clamped to the current last page, so changing list length does not create an out-of-bounds slice. Sorting changes can shift items between pages, consistent with the live-read requirement. Bootstrap wiring and English command registration metadata are accepted exclusions, not findings.

Final verdict: needs corrections
